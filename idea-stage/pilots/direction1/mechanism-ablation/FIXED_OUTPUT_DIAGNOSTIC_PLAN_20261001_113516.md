# 方向一：固定输出长度诊断计划

**日期：** 2026-10-01 11:35（Asia/Shanghai）  
**状态：** 执行前冻结  
**目的：** 在控制每个请求的生成 token 数后，判断树感知放置项是否仍改变树完成时间。

## 动机与边界

上一轮中，树感知策略在 B1、B2 的四树完成时间中位数分别慢 10.28%、10.29%。树 3 的 completion token 只增加 0.45%/0.34%，但树完成时间慢 17.42%/17.12%，逐请求平均客户端 semaphore 等待从约 5.54/5.56 秒升到 8.30/8.32 秒。整体上，树感知组每请求平均客户端等待比 flat 高约 0.85–0.88 秒；每轮服务端 queue mean 也高约 0.43–0.50 秒。

这些日志提供了继续诊断的理由，但不能把等待差异归因到某棵树：客户端 semaphore 在所有并发树之间共享，服务端 queue 统计也只按整轮和副本聚合。树 1、3、5、7 的输出长度和放置都可能影响彼此。

## 设计

- **对照：** `kv-cost-group-flat` 与 `kv-cost-group-tree`；其余服务、路由容量、并发、模型、采样后端和 frozen prompts 保持一致。
- **输入：** 同一 frozen trace 中的树 1、3、5、7，共 38 个请求；两策略的 prompt token 数应逐节点相同。
- **控制生成量：** 每个请求强制生成恰好 256 个 token；请求设 `ignore_eos=true`、`min_tokens=256`、`max_tokens=256`。树/flat 两种策略的输出长度 profile 都设为 inner=256、leaf=256，使路由预测也匹配受控工作量。此模式不用于比较答案正确率。
- **矩阵：** 先跑一棵树的 256-token 长度 sanity；之后跑两个反序 block：B1 flat→tree，B2 tree→flat。每个主运行前都清空两副本的 prefix cache。
- **指标：** 主要指标为四棵树完成时间的中位数；同时单独报告整轮 wall time。记录逐请求放置、客户端 semaphore 等待和 HTTP latency；服务端 queue/prefill/decode 仍按副本整轮报告，不能按树拆分。

## 预设判断与停止规则

- 每个请求必须恰好返回 256 个 completion token 且 `finish_reason=length`；任何一个不满足，当前 run 标为无效并停止后续矩阵。
- 每个主运行的 prompt token 必须与 paired run 逐节点一致。服务端阶段指标观测数不完整时，不解释该 run 的排队结果。
- 只有四个主运行都完成且 queue-pressure gate（每个 run 的加权 mean queue wait ≥0.1 秒）通过，才解释为有服务端排队压力下的诊断。
- tree 在两个 block 中都至少快 5%：记为“等生成量下出现机制信号”，只值得进入独立数据确认；两个 block 都至少慢 5%：当前剩余工作量项在此诊断下不值得继续扩展；其他情况记为 inconclusive。此筛查不改写上一轮自然生成结果，也不支持普遍性、质量非劣或 p95 主张。
- 预算上限 **35 GPU-min**，覆盖启动、校准、sanity、四个主运行和退出；使用空闲 GPU 4–7，预留 5 GPU-min 用于停止与落盘，不运行 local-only/least-loaded 参考项。超时或预算不足即停止，不重启 runtime。

## 下一步决策

若等生成量诊断出现一致的 ≥5% tree 优势，再用更多独立推理树、更多随机/反序 block，并以自然生成作为端到端主结果进行确认。若 tree 仍一致落后，停止扩展当前剩余工作量启发式；若结果混合，则保持未定，不以增加同一小测试集上的重复代替独立样本。
